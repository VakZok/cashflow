# Pinned Go toolchain and CI without CD

The Go version is pinned by the `go` directive in `go.mod`, and CI reads it via `go-version-file` so local and CI cannot drift. `go.sum` is committed. Front-end assets (HTMX, Chart.js) will be vendored into the repo at a fixed version rather than loaded from a CDN, so the host works offline and there is no JS build chain (ADR 0004). The app runs on a Linux host of the user's choice (ADR 0003). CI (GitHub Actions) runs gofmt, `go vet`, the tests, and a CGO-free `linux/arm64` cross-compile check, so small arm64 boards such as a Raspberry Pi keep building. We chose no continuous deployment: the app is built and run on the user's own host, so deploying stays a manual pull, build and systemd restart.

CI is split into one job per concern so a failure is visible at a glance: `style` (golangci-lint with the standard linters plus `sqlclosecheck` and `rowserrcheck`, and gofmt), `test` (`go test -race`), `security` (`govulncheck`, failing the build, also run weekly on a schedule), `shell` (shellcheck on the deploy scripts), and `build` (the `linux/arm64` cross-compile check). Dependabot keeps Go modules and Actions current weekly. We deliberately skipped gosec, CodeQL, secret/container scanning and coverage thresholds: they overlap with the checks above, or do not apply to a single-user app with HTTP-level tests (coverage numbers would push towards testing internals).
